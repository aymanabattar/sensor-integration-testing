01 Overview

There is no custom device API server. Every reading a device sends goes straight into Postgres through a function Supabase exposes automatically as an HTTP endpoint. This is the whole path, in order:

Step 1
Device firmware
Reads sensor, builds JSON, sends one HTTPS POST.
Step 2
rpc/ingest_reading
Validates device_id, inserts one row.
Step 3
device_readings table
Locked by RLS — reachable only through the two RPC functions.
Step 4
Dashboard
Polls rpc/get_readings every 120s and renders it.

A device never talks to the dashboard, and never touches the table directly — it only ever calls ingest_reading. Any client capable of an HTTPS POST works; there is no SDK, no pairing step, no firmware library to install.

02 Authentication

One static key goes in every request header. It is a publishable key — safe to hardcode into firmware, because of what it's scoped to, not because it's hidden.

What this key can do: call ingest_reading, get_readings, and list_devices — nothing else. It has zero direct read or write access to any table, including device_readings itself. That grant boundary is what makes it safe to ship in a public artifact like firmware.

03 Push a reading

This is the one endpoint every device integration needs.

POST https://eribowfxvcmvnieqidow.supabase.co/rest/v1/rpc/ingest_reading

Inserts exactly one reading. Returns no body on success — check the status code, not the response content.

04 Reporting device faults

Faults are first-class fields, not something buried in the raw payload — error_code and error_message are real columns, sent as two extra parameters on the exact same ingest_reading call you already make.

TL;DR — on every call, pass p_error_code (0 when everything's fine) and, when it isn't 0, a short p_error_message. Nothing else about the call changes. The dashboard does the rest — see below.
FieldTypeRequiredMeaning
p_error_codeintoptional, default null0 or omitted = nominal reading. Non-zero = a fault occurred; see suggested ranges below.
p_error_messagestringoptionalShort human-readable detail, e.g. "sensor read timeout after 3 retries".

Suggested code ranges — confirm final list with firmware

RangeCategoryExamples
0NominalNo fault — normal reading.
100–199Sensor100 read timeout · 101 out-of-range value · 102 checksum/CRC failure.
200–299Radio / link200 send failure · 201 no ACK · 202 RSSI below usable threshold.
300–399Power300 low battery · 301 brownout detected.
Still send the numeric fields when you have them. A partial fault (e.g. temperature read fine, humidity sensor timed out) should still populate p_temp_c normally and just carry the fault in p_error_code/p_error_message — don't discard good readings because one sensor on the node failed.
p_raw still exists, separately. Keep sending whatever extra debug context you already put there (battery voltage, boot count, whatever) — it still shows up in the collapsible raw-payload view. error_code/error_message are additional fields, not a replacement for it.

05 Fetch readings

Not required for pushing data — useful for a device (or a bench test) to confirm its own reading actually landed.

POST .../rest/v1/rpc/get_readings

Returns the most recent readings for one device, newest first.

FieldTypeRequired
p_device_idstringrequired
p_limitintoptional, default 50

Requests for p_limit above 500 are silently clamped server-side — you'll never get more than 500 rows back in one call.

06 List devices

Returns every distinct device_id that has ever posted a reading. Handy for a debug tool that needs to enumerate devices without reading the table directly.

POST .../rest/v1/rpc/list_devices

No parameters. Send an empty JSON object as the body.

07 Status & errors

What to check for, in the order a real integration hits them.

204

Reading accepted

No response body. This is the only success case for ingest_reading — don't wait for JSON back.

200

Read succeeded

get_readings and list_devices return 200 with a JSON array — an empty array is a valid, normal response, not an error.

400

Rejected by the function itself

Empty or missing p_device_id raises an explicit error inside ingest_reading. An oversized p_raw (over ~10 KB) fails the table's size constraint. Both come back as a Postgres error message in the body — read it, it names the problem.

401

Direct table access

Calling /rest/v1/device_readings instead of the RPC path returns 42501 — new row violates row-level security policy. This is expected and permanent — the table has no policies, on purpose. If you see this, you're hitting the wrong URL.

08 Limits & security

What the public key protects against, and what it deliberately doesn't.

No per-device identity check. Any caller holding the key can push a reading under any device_id, or read any device's history. Nothing here cryptographically ties a reading to the physical device that claims to have sent it. Fine for an integration-test rig; don't treat it as tamper-proof.
No rate limit is enforced server-side. Keep the device's send interval sane on your end — this endpoint has no backoff or throttling of its own yet.
Payload cap: ~10 KB. p_raw is checked against pg_column_size(raw_payload) < 10000 at insert time. Keep debug payloads lean.

09 Integration checklist

In order, for a new device build.

  • Pick a stable device_id naming convention up front (e.g. master-01) — it can't be changed after readings exist without losing history continuity in the dashboard.
  • Hardcode the apikey header and endpoint URL from Authentication — no token exchange, no login flow.
  • POST to rpc/ingest_reading on whatever cadence makes sense for the sensor; treat 204 as the only success signal.
  • On first bring-up, confirm the reading landed by calling rpc/get_readings for that device, or by opening the dashboard directly.
  • Keep p_raw under the 10 KB cap and self-throttle send frequency — see Limits.
